# 部品の共有とVol管理のルール v1

制定: 2026-09-07（ユーザーの問い「Componentだから全体に変更が影響する物と、独立したものを
Ver1.1・Ver2.1 は別々のものとして取り扱うか？」への回答）
状態: **v1 制定**

---

## 1. 答え: 別々のものとして扱う。ただし「版」ではなく「別のid」として

**部品は参照で共有される。編集は必ず全体に伝播する。**
伝播させたくないなら、**複製して別idにする**。それが「別の版」の正体。

いま実際にこうなっている:

| 部品 | 使っているレイアウト |
|---|---|
| `ipad01_vol12` | `ipad_main`, `ipad_trackball` |
| `ipad01_vol13` | `ipad_v13` |
| `dpad_arrows` | `ipad_main`, `ipad_v13` |
| `default`（Deck） | 3つ全部 |

`ipad01_vol12` を直せば `ipad_main` と `ipad_trackball` の**両方**が変わる。
これは事故ではなく仕様。同じidを指している以上、同じものが出るのが正しい。

---

## 2. レイアウトが部品の中身を上書きする仕組みは作らない

「このレイアウトのときだけキーを1つ変える」ができると便利に見えるが、**作らない**。

理由:

- **役割の分離が壊れる。** いまは レイアウト=配置 / 部品=中身 にきれいに分かれている。
  上書きを許すと、レイアウトの中に中身が混ざる
- **「`ipad01_vol12` はどんな盤面か」に答えられなくなる。**
  どのレイアウトから見ているかを言わないと決まらない、という状態になる
- 差分が2箇所（部品本体とレイアウトの上書き）に散る。片方だけ直して食い違う

代わりに**複製する**。複製は明示的で、追跡でき、片方を壊してももう片方は無傷。

---

## 3. 直すか、複製するか

| 変更の種類 | どうするか | 理由 |
|---|---|---|
| ラベルの誤字、明らかな誤り、壊れているものの修正 | **そのまま直す** | 既存レイアウトを悪化させない。むしろ全部に効いてほしい |
| キーの配置を変える／キーを足す・減らす／体系を変える | **複製して別idにする** | 既存レイアウトを壊しうる |
| 実験・試し | **必ず複製** | 戻せなくなる |

判断に迷ったら複製する。**複製の代償はファイルが1つ増えるだけ**で、
編集の代償は「気づかないうちに別の画面が壊れる」。釣り合っていない。

この運用は過去の事故から来ている（`layouts/layout_ipad_v13.json` の説明に記録:
「以前『キーボードを直したらレイアウトが崩れた』ことがあった」）。

---

## 4. 命名

既存に合わせて `<base>_vol<major><minor>`。

```
ipad01_vol12   … iPad一枚キーボード Vol1.2
ipad01_vol13   … iPad一枚キーボード Vol1.3
```

**注意: ドットの有無が揺れている。** キーマップは `vol12`（ドット無し）、
モックは `mock_layout_editor_vol1.1.html`（ドット有り）。
keymapIdは**ドット無しに統一**する（idは識別子であり、ドットは扱いを面倒にする）。
ファイル名は既存に倣う。

---

## 5. エディタ側の扱い（実装済み・2026-09-07）

区画を選ぶと、その部品が**他のレイアウトでも使われていれば警告を出す**。

> `ipad01_vol12` は他の 1 件でも使われています: **ipad_trackball**
> 中身を直すとそちらにも効きます。片方だけ変えたいなら複製して別idにしてください。

**気づかずに直すのが一番危ない**ので、編集の前に目に入る位置へ置いている。
