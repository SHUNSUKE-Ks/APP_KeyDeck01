## 2. ~~識別IDは新設しない。既にある~~【2026-09-05の裁定で破棄。§7へ】

`canonical_command_id()`（`crates/proto-hub/src/state.rs`）が既にコマンドの正準IDを返している。
これは起動時の許可リストの鍵そのもので、**「Hubが実行を許した単位」＝「記録したい単位」**が一致する。

| アクション | ID |
|---|---|
| `key ENTER` | `key:ENTER` |
| `chord ALT+GRAVE` | `chord:ALT+GRAVE` |
| `text "C:\Users\..."` | `text:C:\Users\...` |
| `tg.fire{fire:chord}` | 中身に潜って `chord:ALT+GRAVE` |
| `key.hold A` / `key.button A` | 両方 `key.hold:A` |

新しいID体系を作ると、許可リストと記録で二重管理になり、T21で踏んだ「入れ子に潜り忘れて片方だけ弾かれる」罠を再発させる。**流用が正しい。**

### 2.1 ここで一つ、意図せぬ効果に注意

IDは「**どこに置かれているか**」を含まない。同じ `key:ENTER` が
キーボードのK220にもDeckのスロットにも居れば、**合算**される。

これは狙いどおりのはず（「Enterというコマンドを何回使ったか」）。
だが「このDeckスロットは使われていない」を知りたいなら別の粒度が要る。
**どちらが欲しいかは裁定事項**（下記 5-①）。

## 3. ファイルを2枚に割る（これが設計の核）

| ファイル | 誰が書く | 中身 | 失ったら |
|---|---|---|---|
| `commands/registry.json` | **人間だけ**（Hubは読むのみ） | id / 名前 / 説明 / When / 製作日 / タグ | 痛い。手で書いた資産 |
| `commands/usage.json` | **Hubだけ** | id / 使用回数 / 最終使用日 / 初回記録日 | 統計が消えるだけ。文章は無事 |

分ける理由は単純で、**Hubのバグや異常終了が、あなたが手で書いた説明文を壊せないようにする**ため。
Hubが触れるのは統計side だけ。最悪 `usage.json` が飛んでも、記録室の中身（名前・説明・When）は残る。

---

## 4. 書き込みの防御（不変条件6を拡張する場合の条件）

1. **書き先は固定パス1つ**（`commands/usage.json`）。パスをクライアントから受け取る口は作らない
2. **マージのみ。削除しない**。未知のIDは足す、既知は数を増やす。消す操作はAPIに持たせない
3. **押すたびに書かない**。メモリ上で数え、`dirty` なら30秒ごと＋終了時にまとめて書く
   （打鍵がディスクI/Oで待たされてはならない。SSD寿命の面でも）
4. **壊れていたら空で起動**。パースに失敗しても panic せず、D9書式でログを出して統計ゼロから再開する
5. `.bak` を残す（D22と同じ作法）
6. 記録するのは**IDと回数と日付だけ**。押した順序・時刻の列は持たない（打鍵ログにしない）

### 4.1 プライバシー上の注意（先に言っておく）

`text:` のIDは**文字列そのものを含む**。あなたのコピペリストはDropboxのフルパスなので、
`usage.json` にパスが平文で載る。

ただし**それらは既に `keymaps/*.json` に平文で入っている**ので、新たに漏れる情報は無い。
問題になるのは「記録室の画面に長いパスがそのまま並ぶ」見た目のほう。
表示側で `registry.json` の「名前」を優先し、IDは折りたたむのが良い。

### 6.1 段階Aだけは先に始める価値がある

使用回数は**集め始めた時点からしか貯まらない**。
記録室の画面（B・C）は後からいつでも作れるが、**Aを後回しにした期間のデータは永久に手に入らない**。

レイアウト部屋やStream Deck拡張より画面としては地味だが、**Aだけ先に入れておく**のが合理的。
段階Aは画面を持たないので、他の作業と衝突しない。

## 7. 裁定（2026-09-05・ユーザー）— §2 と §5① を上書きする

### 7.1 「コマンド」の定義

> エンターはさすがに細かすぎ、キーボードではなく、コマンドは処理の塊の
> スキルやフックスになる前の処理を手動で発動したもの

**打鍵は記録対象外。** 記録するのは「処理の塊」＝Deckスロットやマクロのように、
いずれスキル／フックへ育つ前段の、**手で発動している一まとまりの処理**だけ。

この一言で設計が変わる。§2で「`canonical_command_id` を流用する」と書いたが、**破棄する**。
理由は2つ:

1. あれはキー1個の粒度（`key:ENTER`）であり、まさに「細かすぎ」と言われたもの
2. あれは**アクションの中身から導く**IDなので、同じ `chord:CTRL+S` を持つ別々の
   コマンドが混ざる。「処理の塊」は中身ではなく**役割**で区別されるべき

### 7.2 したがって「名前つきコマンド」を第一級にする

コマンドは、Deckスロットの中身ではなく、**それ自体が独立した登録物**になる。

```
commands/registry.json        ← コマンドの定義（人が書く）
  cmd.obs.start   : { name, description, when, created, action }
  cmd.story.inbox : { ... }

decks/deck_*.json             ← スロットは「参照」するだけ
  { slotId: "S1", commandId: "cmd.obs.start" }
```

**利点**

- IDが役割を表すので、スロットを別のDeckへ移しても**使用履歴が続く**
- 同じコマンドを複数の場所へ置いても1つとして数えられる
- 「名前・説明・When」の置き場所が自然に決まる（コマンド定義そのもの）
- P-003 Ver1-b の**マルチアクション（＝処理の塊そのもの）**と同じ器に収まる

**代償**

Deckのスロットは今アクションを直書きしている。参照方式へ移す**移行が要る**。
ただし現時点でDeckは**2枚しかない**。この移行が最も安いのは今であり、
Deckが増えるほど高くなる。**先に済ませるべき。**

### 7.3 粒度の結論（§5① への回答）

| 対象 | 記録するか |
|---|---|
| キーボードの打鍵（`key:` / `key.hold:`） | **しない** |
| レイヤー切替（`tg.fire`） | **しない**（操作であって処理の塊ではない） |
| トラックボールの移動 | **しない** |
| **Deckスロット等から発動した名前つきコマンド** | **する** |

集計は**コマンド単位**（`commandId`）。置き場所では分けない。
「このスロットが使われていない」ではなく「**このコマンドが使われていない**」を見る。

### 7.4 これで消える問題

- 高頻度の書き込みが無くなる（打鍵は毎秒何度も来るが、コマンド発動は稀）
- `text:` のフルパスがIDになる問題が消える。IDは `cmd.story.inbox` のような人が付けた名前
- `usage.json` が打鍵ログに見えてしまう懸念も消える

### 7.5 月次サイクル（§5⑤ への回答）

> ３、はそれだけでいいです。評価基準はこれから決めます。

**「最終使用日が古い順に並ぶ画面」だけを作る。** 通知機能は作らない。
「何日で棚卸し対象とみなすか」等の評価基準はユーザーが後で決めるため、
**画面側に閾値を焼き込まない**こと。並び順（古い順）と、最終使用日・使用回数の
素の数字を出すに留め、判断は人に残す。
