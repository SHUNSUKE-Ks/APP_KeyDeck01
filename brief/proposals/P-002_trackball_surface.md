# P-002 トラックボール面（State駆動・出口差し替え可能）

起票: 2026-08-01 ／ 起票者: Claude Code（ユーザー着想の受け）／ 状態: 裁定待ち

## 対象アプリ/画面

APP_KeyDeck01。Android端末（Chrome）に新設する**トラックボール面**。
画面上半分がボール、下半分は将来のキーボード面。既存の `/kb` `/deck` `/ipad` と並ぶ4枚目の面。

## 課題

現状KeyDeckで送れるのは「キー」だけで、**ポインタを動かす手段がない**。
外付けマウスを持ち込めない場面（マンガ喫茶のレンタルPC＝P-001と同じ場面、ソファでの操作、
省スペース環境）では、文字は打てるのにカーソルが動かせず作業が完結しない。

## 提案Surface（既存部品の流用を最優先）

**新規の面を1枚追加する。既存のキーボード面・Deck面には手を触れない。**

流用するもの:
- WS接続・token認証・`surface.config`配信・D9エラー書式 … `ipad.html`の骨格をそのまま踏襲
- `SendInput` … `proto-adapter-win` に既にある。マウス移動は同じAPIの別フラグ
- JSON駆動でのフォーマット定義 … `keymaps/` と同じ「JSONが正、コードは道具」の原則

新規発明は「ボールの描画」と「状態の受け渡し方」の2点だけに絞る。

### 描画（D2判断は解決済み）

Three.jsは使わない。**Canvas 2Dのみ**で球を描く（単位球面上の点＋大円2本を回転行列で正射影）。
外部ライブラリ・CDN・ビルド工程はゼロ。D2に一切触れない。検証済みモック:
`（scratchpad）trackball_canvas2d.html` — 23KB・単体完結・Android実機で動作確認済み。

## 必要な新規要素と実現可能性

### 中核: 3層に分ける（今回の主眼）

ユーザー要望「あとで付け替えるかもしれないから機能を分離」への回答。
**面は「何を操作しているか」を知らない。** 出口の決定はHub側のJSONが持つ。

```
[面] ボールを回す ──emit──▶ [State] ──binding──▶ [出口]
  Canvas 2D             正規化された状態          今日: mouse.move
  出口を知らない          機器に依存しない          将来: 3d.angle / gamepad.axis
```

### State（機器非依存の共通形。ここが差し替えの軸）

```json
{
  "delta":  { "dx": 12, "dy": -3 },
  "spin":   { "x": 0.0, "y": 0.0, "z": 0.0, "w": 1.0 },
  "active": true
}
```

| 項目 | 意味 | 主な読み手 |
|---|---|---|
| `delta` | 直前フレームからの相対移動量 | **マウス（今回）** |
| `spin` | 累積姿勢（クォータニオン） | 3D角度（将来） |
| `active` | 接触中か | ゲームパッド（離したら中立へ戻す・将来） |

**今回はマウスのみ実装する**が、`spin`・`active`は最初から**送るだけ送っておく**。
Hub側は読み捨ててよい。後から3D/パッドを足す時にプロトコル改版が要らなくなるため。

### WSメッセージ（面の種類に依らない汎用名にする）

```json
{ "t": "surface.state", "surfaceId": "tb01", "delta": {...}, "spin": {...}, "active": true }
```

`trackball.move` ではなく `surface.state` とするのは、将来の3D面・パッド面が
**同じメッセージを再利用**できるようにするため。ここが「分離」の実体。

### binding（出口の宣言。JSONが正・コード変更不要）

```json
{ "id": "tb01", "type": "trackball", "binding": { "t": "mouse.move", "clamp": 200 } }
```

出口の差し替え＝**このJSONの1行を書き換えるだけ**。`{"t":"3d.angle"}` に変えれば
同じ面がそのまま3D操作になる（G4「フォーマット変更にコード変更不要」と同じ思想）。

### アーキ不変条件1との関係（**要裁定・本提案の核心**）

条件1は2つの文からなる。**触れるのは前半だけ**である。

| 条文 | 抵触 |
|---|---|
| 「クライアントは位置ID(keyId/slotId)**のみ**送信し、キー解決はHub側」 | **「のみ」に抵触**。dx/dyは位置IDではない |
| 「**任意vk/文字列**を受けるWS APIを追加しない」 | **抵触しない**。dx/dyはvkでも文字列でもない |

条文が理由として挙げるのは「許可リスト防御が無効になるため」。
その観点では、**防御の仕組み（クライアントの語彙 ⊆ 事前宣言された集合）は保たれる**:

- クライアントは `binding` を**指定できない**。送るのは `surfaceId` と正規化状態のみ
- どの出口に繋がるかは**Hub側のJSONだけ**が決める（keyIdをHubが解決するのと同じ構造）
- クライアントは「マウスを動かせ」とすら言えない。言えるのは「tb01が(dx,dy)動いた」だけ
- 任意vk・任意文字列・任意コマンドは一切増えない。増えるのは**上下限つきの整数2つ**

### 危険度の実態評価（過大評価しないための記録）

**マウス移動の追加による実質的なリスク増分は小さい。** 理由:

- KeyDeckは既にキーマップ次第で `Ctrl`/`Alt`/`Win` 系の組み合わせを送れる。
  `Win+R` が送れる時点で、tokenを持つ相手はPCをほぼ自由に操作できる。
  ポインタ操作を足しても到達範囲の増分は限定的
- 送るのは相対移動量であり、**一般のUSB HIDマウスと同一の形**
  （HIDブートプロトコル＝ボタン＋dX＋dYの3バイト。Logicool/Elecomの
  トラックボールもOSからは通常のマウスとして見える）。業界標準から外れた設計ではない

したがってD番号を取る目的は**リスク管理ではなくガバナンス上の明確化**である。
次にCLAUDE.mdを読むAIが「この種のメッセージは正規のものであり、その境界はここまで」と
判断できる状態にすること。**独断で条文を読み替えないため**にFABLEの裁定を求める。

### 安全側の措置

- `dx`/`dy` は1メッセージあたり ±200 でクランプ。超過は D9書式で拒否（`SURFACE_STATE_RANGE`）
- 送信レート上限（125Hz相当）。超過分は捨てる
- `binding` は事前登録の許可リストのみ。未知の binding はロード時に拒否
- 画面外へカーソルが逃げる以上の被害は原理的に起きない（任意実行経路を作らない）

### Rust側の変更量（いずれも既存の延長。新規crateなし）

| crate | 変更 | 規模 |
|---|---|---|
| `proto-adapter-win` | `mouse_move(dx,dy)`。`SendInput`＋`MOUSEEVENTF_MOVE`（相対） | 小。既存`send()`と同じ形 |
| `proto-keymap` | `Binding` enum＋`type:"trackball"`のsurface定義とスキーマ検証 | 中 |
| `proto-hub` | `surface.state` 受信 → binding解決 → adapter呼び出し | 小 |
| `static/trackball.html` | 新規1枚 | 中（モック流用） |

`crates/hub-core/` は触らない。既存のキーマップ・Deck・iPad面のコードにも変更を入れない。

## 受け入れ基準案（G形式）

- **G-a** Android実機でボールをドラッグすると、PCの実カーソルが対応方向へ動く
- **G-b** 面のJSファイルに "mouse" という語が**1つも出てこない**（出口を知らないことの機械的な確認）
- **G-c** Hub側JSONの `binding` を別の値へ書き換えるだけで出口が変わる。**面のコードは無変更**
- **G-d** `dx`/`dy` に範囲外の値を送ると `SURFACE_STATE_RANGE` で拒否され、Hubは落ちない
- **G-e** `spin`・`active` は今回未使用だが、Hubが受信して読み捨てても警告・エラーにならない
- **G-f** `cargo test --workspace` が既存54件＋新規分すべてpass（既存テストの弱体化なし）
