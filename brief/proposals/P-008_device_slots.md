# P-008 端末スロット — 端末に名前を付け、盤面を端末ごとに覚える

起票: 2026-09-30 ／ 起票者: Claude Code（Opus 5.5・KeyDeck 統括チャット）／ 状態: **提案（利用者の裁定待ち）。実装していない**

## 利用者の要望

- 接続する端末を**最大3台**にする（iPad 1台＋Android 2台）
- 編集画面で**3台を並べて表示**し、1台ずつ編集する（編集中の端末は常に1台。header の名前の横に緑の●）
- 未接続の端末は、その端末の枠に QR を出して繋ぐ（`/connect` の「どの QR がどの端末用か分からない」を解消する）

## いまの仕組みでは足りないところ

**Hub は端末を区別していない。** 繋がった WebSocket に通し番号（`ClientId`）を振るだけで、名前も「どの盤面を出しているか」も持たない。

| 起きること | 理由（コード） |
|---|---|
| iPad で「盤面を移る」を押すと、Android も同じ盤面に変わる | `layout.switch` は `broadcast_to(SurfaceKind::Layout, …)`＝**/layout を開いている全端末へ一斉送信**（`ws.rs` の `fire_action`） |
| 編集画面は「どの端末に何が出ているか」を知らない | 端末の一覧を返す API が無い。`/connect` は画面の種類ごとの QR を並べるだけ |
| 盤面の初期値は Hub に1つだけ | 「最初に出す board」は全端末共通 |

### 分割キーボード（左右）が動いたのはなぜか

**左右は「同じ1つのものを、URL で半分ずつ見ている」だけだから。** 端末の区別は要らなかった。

- 左の端末は `/kb?half=left`、右は `/kb?half=right` を開く。**どちらの半分を描くかは URL が決める**（`static/kb.html` が `half` を読んで、共通の構成から自分の半分だけ描く）
- 押したキーの意味・レイヤーの状態は、左右で**1つを共有**する。左で Fn を押すと右もレイヤーが変わる（そうでないと困る）
- つまり「2台で1台のキーボード」。**3台がそれぞれ別の盤面を出す**今回の要望とは逆向き

今回ほしいのは「3台がそれぞれ**別の**盤面を持ち、1台で盤面を移っても他の2台は変わらない」こと。
ただし**端末に名前を渡す方法は、分割キーボードと同じ「URL に書く」でよい**（下の案）。

## 案

### 1. 端末スロットを Hub の JSON で先に決める（読み取り専用）

`devices/devices.json`（新規・手で書く。Hub は読むだけ＝**書き込み口は増えない**）:

```json
{
  "devices": [
    { "id": "ipad",     "label": "iPad 12.9（リビング）", "kind": "tablet", "orientation": "landscape", "defaultLayout": "note_story" },
    { "id": "android1", "label": "Android 1（机の左）",   "kind": "phone",  "orientation": "portrait",  "defaultLayout": "game_iphone7_port" },
    { "id": "android2", "label": "Android 2（机の右）",   "kind": "phone",  "orientation": "portrait",  "defaultLayout": "iphone7_portrait" }
  ]
}
```

- `id` は `[a-z0-9_]{1,32}`。**最大3件**（超えたら起動時に拒否）。`defaultLayout` は実在する盤面だけ（起動時に確かめる）
- ファイルが無ければ**今までどおり**（端末の区別なし・一斉送信）。既存の使い方を壊さない

### 2. 端末は URL で自分のスロットを名乗る

- QR の URL に `&device=android1` を足す（`/layout?device=android1&token=…`）。分割キーボードの `half=` と同じ形
- Hub は接続時に `device` を読み、**devices.json に無い id は拒否**（`WS_DEVICE_UNKNOWN`）
- **不変条件1とは衝突しない**: 端末が送るのは「登録済みのスロットの id」だけで、何のキーが出るかには関わらない（`surface=` や `half=` と同じ種類の値）

### 3. 盤面は端末ごとに覚える

- Hub の状態に「端末 id → いまの盤面」を持つ。接続したら、その端末の今の盤面（無ければ `defaultLayout`）を配る
- **`layout.switch` は押した端末のスロットにだけ送る**（同じ id で繋いでいる端末が2つあれば両方）。`device` なしで繋いだ端末は今までどおり一斉送信
- 覚えるのはメモリだけ（Hub を再起動すると `defaultLayout` に戻る）。書き込み場所を増やさないため。永続化は別件（設定の永続化と同じ裁定が要る）

### 4. 編集画面に端末の一覧を出す（読み取り専用 API）

`GET /api/devices?token=` → 各スロットの `id`・`label`・`kind`・`orientation`・**接続中か**・**いまの盤面**。
統合編集画面（`00_勉強フォルダー/38_…モック`）の3台並べ表示と、未接続の枠に出す QR はこれを使う。

## 決めてほしいこと（利用者）

1. **盤面を移るのは「押した端末だけ」でよいか。** 「iPad で押したら3台とも移る」ボタンも欲しいなら、`layout.switch` に `"to": "all"` を足す（既定は押した端末だけ）
2. **レイヤー（Fn）の状態はキーマップごとのまま**でよいか。同じキーマップを2台に出していると、片方の Fn でもう片方も変わる（今の分割キーボードと同じ）。端末ごとに分けたいなら、別の設計が要る（D3 に関わる）
3. 端末の名前・台数・向きは **devices.json を手で書く**運用でよいか。画面から変えたいなら、書き込み場所を1つ増やす裁定が要る（不変条件6）

### 利用者の回答（2026-09-30）

- 3（devices.json を手で書く）: **OK**
- 2（レイヤー）: 利用者案「レイヤー切り替え専用の修飾キーを、端末ごとに別々に作ればよい」。
  → **端末ごとにキーの組（キーマップ）を分ければ、そのとおり独立する**（レイヤーの状態はキーマップごとなので、別のキーマップなら互いに影響しない）。コードの変更は要らず、D3 も変えない。同じキーマップを2台に出したときだけ連動する（分割キーボードで使っている性質なので、なくさない）
- 1（盤面を移る）: **既定は押した端末だけ。3台そろって移る動作もコマンドとして用意する**（`layout.switch` に `"to": "all"`）。アプリ切り替えなどで3台同時が要る場面には、利用者が明示して取り付ける（Hooks）。**勝手に全台にしない**

### 利用者の裁定（2026-09-30・実装前）

- **新しい編集画面は今の Hub の中に作る**（素の HTML/JS・新しい URL。旧画面は凍結して残す）。CH への移動はその後
- **表示レイアウト（header の「KeyDeck」から選ぶ表示の組み合わせ）は Hub に保存する** → 書き込み場所を1つ増やす（`views/view_<id>.json`。不変条件6に追記して、他の保存と同じ守り: id の形の検査・`.bak`・読み直し）。実装は編集画面の段階で行う
- **部品棚の既定は左のパネル**（下の棚・重ねる／並べるは NAV 設定で選べるように残す）
- 見た目の土台は `00_勉強フォルダー/41_統合編集画面_VIA型モック_v0.4.html`（v0.4.1）
- 端末3台の実物（名前・機種・向き）は未回答。段階A は `devices/devices.example.json` だけ置き、**`devices.json` が無ければ今の動きのまま**にして進める

## 段階

| 段階 | 中身 | 触る所 |
|---|---|---|
| A | devices.json の読み込みと検査、URL の `device`、端末ごとの盤面、`layout.switch` の送り先 | `startup.rs`・`state.rs`・`ws.rs`・`static/layout.html`・テスト |
| B | `GET /api/devices` と、`/connect` の QR を端末ごとにする | `ws.rs`・`gallery.html` |

段階A だけで「3台がそれぞれ別の盤面」は実現する。B・C は画面の話。

## 変えないもの

- 任意のキー・任意のパスを受ける口は作らない（端末が名乗れるのは登録済みの id だけ）
- `hub-core` は触らない
- devices.json が無い環境では、今の動きと1つも変わらない
