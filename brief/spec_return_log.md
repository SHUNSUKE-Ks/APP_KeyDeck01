## SR-001: ipad01_vol12のラベル二段表示・記号盤の全角(amber)強調・data-sym値の逐語転記
- 起票: Sonnet / 2026-07-20 / 対象: `static/ipad.html`・`keymaps/layers/ipad01_vol12_layer0.json`・`layer2.json`（D19/D20/D24、`brief/mockup/screen_mock_v0.4.html` ①）
- 内容: 3点、いずれも機能（G12/G13・文字入力・レイヤー切替）はブロックしないが表現の解釈が必要だった。
  1. モックの `,` `.` `?` キーは通常時に小書きヒント(`<small>、</small>,` 等)を上に表示する二段ラベル。T7の`KeyDef`は`{label, action}`のみでsubLabel相当のフィールドが無いため、`label`文字列に`"\n"`を区切りとして埋め込み（例`"、\n,"`）、`ipad.html`側で1行目を`<small>`・残りをメインテキストとして描画する自前規約にした（スキーマへの新フィールド追加はしていない）。
  2. モックは記号盤トグル時、全角記号キーに`.zen`クラス（アンバー文字色）を付ける。`KeyDef`に全角/半角の真偽値フィールドが無く、文字コード帯での判定も「…」(U+2026)のような例外があり信頼できないため、**T8では色分けを実装せず全記号キーを同一スタイルで表示**した（記号自体は全て`text`アクションで指定どおり正しく入力される。差はアンバー強調の有無のみ）。
  3. モック内の`,`(K410)`.`(K411)`?`(K412)キーの`data-sym`属性値がそれぞれ`：`(全角コロン)`；`(全角セミコロン)`〜`(全角チルダ)になっており、視覚的な小書きヒント(、/。/？)と一致していない（記号盤トグル時は`data-sym`の値がそのまま表示される仕様のため）。「モックの`data-sym`属性の内容を全部textアクションで」という指示に従い、**この値をそのまま逐語転記**した（`keymaps/layers/ipad01_vol12_layer2.json`のK410/K411/K412）。ヒント文字と実際に入る記号が食い違って見える可能性がある。
- 裁定（2026-07-20 FABLE）:
  1. **承認**。`label`内`"\n"`区切り（1行目=小書き・以降=メイン）を暫定正規規約とする。T9でKeyDefへ`sub`フィールドを追加した時点で移行
  2. **承認**。アンバー強調はフェーズAでは省略でよい。T9のKeyDef拡張（`zen`相当の真偽値）で対応
  3. **typoではなく意図どおり**。記号盤では 。、？ が数字段（K101〜）に既に配置されているため、`,`/`.`/`?`キーには別の全角記号（：；〜）を割当てた。基盤の小書きヒント（、。？）は「IME全角時の変換結果」の説明であり記号盤の割当とは無関係。逐語転記で正しい

## SR-002: T10で`crates/proto-hub/src/deck.rs`への1行追加が必要（設計書v0.6の触ってよいファイル表に未記載）
- 起票: Sonnet / 2026-08-01 / 対象: `crates/proto-hub/src/deck.rs`（`brief/keydeck_trackball_design_v0.6.md` §2 触ってよいファイル表、T10-1）

  1. `crates/proto-keymap/src/lib.rs`の`validate_merged`（vk辞書チェック）— 触ってよい（Action追加のみ、と明記）
  2. `crates/proto-keymap/src/lib.rs`の`resolve()` — 同上、同ファイル内
  3. `crates/proto-hub/src/deck.rs`の`load_deck_str`内のDeckスロット検証 — **v0.6の「触ってよいファイル/禁止ファイル」表に一切登場しない**（`decks/`＝JSONデータディレクトリは禁止と明記されているが、そのローダーである`deck.rs`自体は触ってよい/禁止どちらの欄にも無い）

- 裁定: （FABLE記入待ち。次回設計書更新時に「触ってよいファイル」表へ`crates/proto-hub/src/deck.rs`を追記いただけると今後この種のSRを避けられます）

## SR-004 トップ画面を「設定」ではなく「レイアウト編集」にした（2026-09-07）

- 起票: Claude Code（Opus 5）／状態: **ユーザー指示により実装済み。設計書との食い違いを記録**
- 対象: `brief/keydeck_design_v0.3.md` の **D15**

**設計書の記述（D15）**

> `/` を設定画面に置換（v0.2のQR3枚並びランディングは廃止）。
> 一覧行=［フォーマット名｜kind｜QRボタン｜URL文字列］。
> QRボタン→モーダルポップアップに**そのフォーマット1枚だけ**のQRを大きく表示

**実際にどうしたか**

| URL | D15の想定 | 実装 |
|---|---|---|
| `/` | 設定画面 | **レイアウト編集（`editor.html`）** |
| `/connect` | （規定なし） | QRギャラリー（`gallery.html`）。カード右上のQRボタンで1枚だけ表示 |
| `/settings` | （`/` に置く想定） | 設定画面。一覧＋QRモーダル（**D15の行構造とQRモーダルはここで満たしている**） |

**なぜ食い違ったか**

2026-09-07 のユーザー指示:
「QRはトップでなく専用ページを作成してほしい。Gallery式にして…」
「トップは、今回作ったHTMLkeyboardレイアウトを変えれる画面にしてくれませんか？」

**D15の意図（QRの縦並びランディングを廃止し、トップを操作画面にする）は満たしている。**
違うのは「トップに置く操作画面が、設定ではなくレイアウト編集になった」点のみ。
D15が要求した一覧行の構造とQRモーダルは `/settings` と `/connect` に分けて実装済み。

**これがSRである理由**

`brief/` 配下の設計書は凍結領域（SR起票のみ可）。設計書を読んだAIが
「`/` は設定画面のはず」と判断して差し戻す危険があるため、記録を残す。

**裁定待ち**: 設計書側をどう扱うか。
- 案A: D15を「トップ＝主たる操作画面。中身はレイアウト編集」と読み替え、実装を正とする（当面これ）
- 案B: `keydeck_design_v0.6.md` を起こしてD15を改訂する
