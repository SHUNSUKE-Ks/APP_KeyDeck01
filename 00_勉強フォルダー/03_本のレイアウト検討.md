# 本のレイアウト検討

対象原稿: `02_KeyDeck技術書_初稿.md`

この本は、非エンジニアが「全体像」から入り、必要になったときだけ関数の細部へ降りられる
構造にします。初稿では読みやすさを優先してMarkdownの見出し・表・コード枠だけで組みました。

## 採用した基本形

```text
章扉
  この章の問い
  全体図または短い結論

本文
  仕組みを日常語で説明
  小さなコード引用

関数カード
  役割 / 場面 / 入力 / 処理順 / 出力 / 失敗時 / 関連 / 例え

章末
  できるようになったこと / 扱わなかったこと / 確認問題
```

この順番なら、コードをまだ読めない人は本文と例えだけを先に読めます。コードを追いたい人は
関数カードの出典から `notes/` と実ファイルへ戻れます。

## 決めていきたい四点

| 論点 | A | B | 初稿の状態 |
|---|---|---|---|
| 章扉 | 各章を独立ページ風に大きく見せる | 見出しだけで連続して読ませる | B |
| 関数カード | 本文の直後に置く | 章末にまとめる | 本文直後 |
| 図 | Mermaid等の図を多用する | 文字による小さな図だけ使う | 小さな図 |
| 確認問題の答え | 巻末に解答を置く | 解答なしで考える余白を残す | 解答なし |

## 次の確認で見たいこと

1. 第1章から第3章までを読んで、コードに入る前の説明量は多すぎないか。
2. 第5章の`resolve`関数カードは、非エンジニアでも「状態が変わる」と「入力が出る」の違いを追えるか。
3. 章末の確認問題は、勉強の助けになるか、読書を中断する感じが強いか。
4. 表が多いか、図を増やしたいか。
