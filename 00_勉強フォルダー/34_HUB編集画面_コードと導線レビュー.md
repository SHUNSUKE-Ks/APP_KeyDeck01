# HUB（PC側編集画面一式）レビュー — コードと操作導線の見直し・改善点

作成: Claude Code（Sonnet 5） 2026-09-28。**実装はしていない。観察と改善点の提案のみ**（vision v1 §2の explorer 役に相当）。

## 対象

PC側の編集画面8枚（`crates/proto-hub/src/ws.rs` のルーティング、`static/components.js` の `NAV_TREE` で束ねられているもの）。

| 画面 | パス | 役割 |
|---|---|---|
| レイアウト編集 | `/` | 区画（部品の配置）を編集。**現在のトップ画面**（2026-09-07裁定） |
| レイアウト編集 V2（新View） | `/editor_v2` | 同じboardを編集する新しい見た目。旧版と並存 |
| キー編集 | `/keys` | 盤面上でキーの割り当てを直接編集 |
| Deck編集 | `/deckedit` | Deckのタイルを編集 |
| 接続（Gallery） | `/connect` | 端末を繋ぐためのQR一覧 |
| 操作カタログ | `/catalog` | 動作(action)の一覧 |
| スキーマ・辞書 | `/schema` | VK辞書等の一覧 |
| 設定 | `/settings` | テーマ切替・再読込 |

比較材料として `30_依頼_キーボード編集Viewの見た目.md`／`31_キーボード編集View_3案.html`／`32_キーボード編集View_デザインメモ.md`（別チャットへ依頼済み・未評価のまま眠っていた3案とデザインメモ）を読み、現行実装と突き合わせた。

## 良い点（壊さないよう先に明記）

- **キー編集(`/keys`)は既に「実機と同じ盤面の上で直接編集する」思想**（32_のC案「実機」と同じ方向）。データ構造を読ませるフォームではなく、盤面のキーをそのまま押す・つかむ操作になっている。
- 保存系（レイアウト・キー・Deck）は「保存前に不正形を検出→押せなくする→保存後に読み直して検証→失敗したら巻き戻す」という同じ型で統一されている（CLAUDE.md不変条件6の書込4箇所と一致）。
- `components.js` に色・見出し・トースト等の共通部品を集約し、画面が増えても直す場所が1か所で済む構造になっている。

## 改善点

### A. 導線（操作フロー）

1. **「ホーム」の指し先が画面ごとに割れている（実装のブレ、直すべき）**
   `renderSubHeader` のbreadcrumbで、`editor.html`・`editor_v2.html`・`keys.html` は `{ label: "ホーム", path: "/connect" }`（接続/QR画面）を指すが、`deckedit.html` だけ `{ label: "ホーム", path: "/" }`（レイアウト編集）を指す。
   2026-09-07の裁定は「トップは`/`（レイアウト編集）、QRは`/connect`へ分けた」なので、**「ホーム」は`/`を指すのが筋**。3画面が古いままになっている可能性が高い。
   （該当: `static/editor.html:1036`, `static/editor_v2.html:1162`, `static/keys.html:203`, 対比 `static/deckedit.html:206`）

2. **8画面のうち4画面にしか「現在地」パンくずが無い**
   `renderSubHeader`（パンくず＋この画面固有の操作ボタン）を使っているのは レイアウト編集／V2／キー編集／Deck編集 の4つだけ。
   接続(`/connect`)・操作カタログ(`/catalog`)・スキーマ(`/schema`)・設定(`/settings`) は `renderNav`（右上の「KeyDeck▼」ドロップダウンだけ）のみで、パンくずも画面固有アクション帯も無い。
   同じアプリの中で「今どこにいるか」の見せ方が画面によって違う状態。

3. **設定画面のリンク文言が古い（実害のある表記ミス）**
   `static/settings.html:117` に `<a href="/">QRランディングページ →</a>` が残っている。
   `/`は2026-09-07以降「レイアウト編集」であり、QRの一覧は`/connect`に移っている。**リンク先(`/`)自体は今も踏めるが、文言が指している内容（QRランディング）とは別物**なので、初見の人が押すと「レイアウト編集画面が開く」ことになり混乱する。

4. **「KeyDeck▼」ドロップダウンは3グループ・最大15項目のフラットな縦一覧**
   `NAV_TREE`（PC部門8／ゲーム部門7／保存版2）が見出し文字だけで区切られ、色・アイコンでの区別が無い。部門が増えるほど「今探しているのはどの部門の項目か」を文字だけで判別することになる。
   （該当: `static/components.js:1108`〜）

5. **「レイアウト編集」と「V2（新View）」のどちらを使うべきかが画面上に出ていない**
   コード内コメントには「新Viewは置ける部品を探しやすく作り替えたもの」とあるが、この説明はメニュー上にはなく、ソースを読まないと分からない。両方とも同じboardを編集できるため、初めて触る人がどちらを選ぶべきか判断できない。

### B. 見た目（ビジュアルの質感）

6. **色・状態表現のトークンが画面ごとに個別定義で、状態の見せ方に一貫した設計が無い**
   `editor.html`は`:root`に`--bg/--panel/--accent/--ok/--err/--warn`等を直書きしており、画面ごとに似た値を個別に持っている。
   一方、32_のデザインメモは「通常／押下中／選択中／修飾中／空き／修飾で変わる」という**状態の一覧とCSS変数（陰影・角丸・モーション時間まで含む）**を体系立てて定義している。
   現行の編集画面には「押した感」（沈む・波紋・光る）や「空き」の専用表現（破線枠）が無く、`.selected`／`.bad`（赤）以外の状態表現が薄い。

7. **モーション（動きの長さ）の設計が無い**
   32_は`--t-press 70ms`／`--t-fast 140ms`／`--t-med 220ms`など用途別に時間を決め、`prefers-reduced-motion`にも対応している。
   現行画面はトースト（`SUB.toast`）以外に目立つトランジションが無く、「触って気持ちいい」感触は今のところ狙われていない（機能優先の開発者向けUIの段階）。

8. **情報密度が高く、文字（13px基準）中心のレイアウト**
   3列グリッド（190px／可変／260px）にJSON生プレビューまで出す構成で、開発中の確認には向くが、"見た目のUI向上"という観点では詰め込み型。31_のB案（カード集計＋色で一覧）のような**数と色でひと目で分かる見せ方**は未導入。
