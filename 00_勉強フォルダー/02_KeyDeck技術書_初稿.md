- 対象は **Windows** です。PCへの実入力は Windows の SendInput を使います。

- この仕組みは LAN 内の自分の PC を操作するためのものです。認証を外す方法、
  インターネットへ公開する方法、任意のコマンドを送る構成は載せません。

# 第I部　設計を先に決める

## 第1章　何を作ったのか

KeyDeck は、PCで動く **Hub** と、スマホ・タブレットで開く **ブラウザ端末** の組です。
端末は画面上のボタンを押した場所を知らせ、Hub がその場所の意味を JSON から調べ、
Windows に入力を送ります。

```text
ブラウザ ──「K101を押した」──> Rust Hub ── SendInput ──> Windowsの前面アプリ
               位置ID                JSONで意味を解決
```

ここで大切なのは、ブラウザが「Ctrl+Zを実行して」とは言わないことです。ブラウザが言えるのは
「K101を押した」だけです。意味の決定を PC 側に残すため、端末を増やしても同じルールで守れます。

### この章でできるようになったこと

- Hub、ブラウザ端末、JSON の役割を区別できる。
- 「位置」と「意味」を分ける理由を説明できる。

### 扱わなかったこと

- Tauri でHubを包むこと、モバイルアプリ化、インターネット越しの操作。

### 確認問題

1. ブラウザが送るべきなのは、キーの意味と位置のどちらでしょうか。
2. 意味をHubで決めると、どんな変更が安全になりますか。

## 第2章　先に決めた安全の境界

KeyDeck の不変条件は「クライアントが送るのは位置ID、または範囲を決めた面の状態だけ」です。
Hub 側には、起動時に読み込んだ JSON から作る **allow list（許可リスト）** があります。
知らない位置ID、知らない操作、壊れたJSONは実行まで届きません。

トラックボールのような連続値は例外ですが、`surfaceId` と上限のある移動量だけを送ります。
どのWindows操作へつなぐか（binding）は、やはりHub側のJSONが決めます。

### 関数カード　`canonical_command_id`

出典: `C:\00_master\DevApps\APP_KeyDeck01\crates\proto-hub\src\state.rs` の `canonical_command_id`

- **役割**: Actionを、許可リストで比較できる一定の識別子へ変換します。
- **呼ばれる場面**: 起動時に、JSONに書かれた許可済みアクションの集合を作る場面です。
- **入力**: `Action`。たとえばキー、キー組合せ、文字入力、押しっぱなしです。
- **処理順**: Actionの種類を調べ、同じ意味の操作が同じ文字列になるよう正規化します。
- **出力**: 比較用のID、または実行対象でなければ `None`。
- **失敗時**: 実行する関数ではないためWindows入力は発生しません。
- **関連関数**: `startup::all_actions`、`ws::fire_action`。
- **例え**: 受付で「この人は入館名簿に載っていますか」を照らすための社員番号です。

### この章でできるようになったこと

- token、allow list、位置IDがそれぞれ守る場所を説明できる。

### 扱わなかったこと

- tokenを無効にする手順、外部公開のネットワーク構成。

### 確認問題

1. クライアントが任意のVK名を送れると、なぜallow listが弱くなりますか。
2. `surface.state`が位置IDだけの原則を破らない条件は何ですか。

## 第3章　JSONを正にする

KeyDeckでは、キーの盤面は `keymaps/`、Deckのボタン集は `decks/`、画面の区画割りは
`layouts/` に置きます。コードは「そのJSONを検証し、表示し、実行する道具」です。

```text
keymap manifest ─┐
layer JSON       ├─> 読込・検証 ─> Keymap ─> ブラウザの盤面
deck JSON        ┤
layout JSON      ┘
```

この分離があるため、たとえば十字キーをトラックボールに取り替える変更は、画面HTMLを書き直さず
layout JSON の `component` を変えることで表せます。ただし、JSONは自由帳ではありません。
schemaとロード時検証を通る必要があります。

### この章でできるようになったこと

- keymap、layer、Deck、layout の担当を見分けられる。
- 「JSONを編集する」と「任意の設定を受け入れる」の違いを説明できる。

### 扱わなかったこと

- 未実装の部品作成GUI、任意ファイルのアップロード。

### 確認問題

1. 画面上の配置を変えるとき、まず確認すべきJSONは何ですか。
2. schemaだけでなく実装側の検証も必要なのはなぜですか。

# 第II部　Hubが止めるべきものを止める

## 第4章　起動時に全部検査する

途中まで読めた設定を使い始めると、「画面は半分だけ新しく、Hubの状態は古い」という
追跡しにくい事故になります。KeyDeckはディレクトリを走査し、関連するデータを揃えて読み、
すべて検証できたときだけ新しい構成を使います。これが **ロード時検証** と、
**部分適用しない** という方針です。

### 関数カード　`load_startup_data`

出典: `C:\00_master\DevApps\APP_KeyDeck01\crates\proto-hub\src\startup.rs` の `load_startup_data`

- **役割**: keymap、Deck、Surface、layoutをまとめて探索・読込・相互検証します。
- **呼ばれる場面**: Hub起動時と、正規の再読込時です。
- **入力**: 各JSONを置いたディレクトリです。
- **処理順**: ファイル発見 → 個別の構文・schema検証 → ID重複確認 → layout参照先の実在確認 → 許可リスト作成、の順です。
- **出力**: Hubが安全に使える起動データ一式です。
- **失敗時**: エラーとして返し、壊れた一部だけを採用しません。
- **関連関数**: `discover_prefixed_json`、`layout::load_layout_from_path`、`all_actions`。
- **例え**: 出発前に全員の乗車券と行き先を確認し、1人でも不整合なら列車を出さない改札です。

### この章でできるようになったこと

- 「再読込」が単なるファイル読み直しより慎重な操作であると分かる。

### 扱わなかったこと

- 壊れた設定を無理に救済する自動修復。

### 確認問題

1. layoutが存在しないkeymapを参照したら、いつ拒否されるべきでしょうか。

## 第5章　レイヤーを決定的に解く

レイヤーは「いま有効な番号のうち、大きい番号から探す」ルールです。`trans` は
「この層では決めないので下の層へ渡す」という意味です。押している間だけの `momentary` と、
押すたびに残る `toggle` を状態として分けて持ちます。

```rust
// 説明用に周辺のエラー処理を省いた引用
let active = state.active_layers();
for layer_id in active.iter().rev() {
    if let Some(layer) = keymap.layer(*layer_id) {
        if let Some(def) = layer.keys.get(key_id) {
            if !matches!(def.action, Action::Trans) {
                found = Some(&def.action);
                break;
            }
        }
    }
}
```

出典: `C:\00_master\DevApps\APP_KeyDeck01\crates\proto-keymap\src\lib.rs` の `resolve`（746行目付近）。
この抜粋は説明用に簡略化しています。

### 関数カード　`resolve`

- **役割**: `keyId` と押下／解放から、状態変更か実入力かを決定します。
- **呼ばれる場面**: `key.press`をHubが受けたときです。
- **入力**: `Keymap`、可変の`LayerState`、位置ID、`Edge::Down`または`Edge::Up`。
- **処理順**: keyの存在確認 → 有効レイヤーを降順に探索 → `trans`を通過 → Action別に状態変更または発火を返します。
- **出力**: `LayerChanged`、`Fire`、`FireAndLayerChanged`、`Ignored`、エラー相当の解決結果です。
- **失敗時**: 未知キーは`UnknownKey`、定義が見つからなければ`NoResolution`です。panicしません。
- **関連関数**: `LayerState::active_layers`、`ws::handle_key_press`。
- **例え**: 透明なシートを上から順に重ね、見える最上段の指示を採用する作業です。

### この章でできるようになったこと

- momentary、toggle、trans、優先順位を小さな例で追える。

### 扱わなかったこと

- レイヤー意味論の別案。D3のルールは固定です。

### 確認問題

1. レイヤー2が`trans`で、レイヤー0にキー定義があるときは何が起きますか。
2. 同じ入力列が常に同じ結果になることは、調査にどう役立ちますか。

## 第6章　WebSocketで「位置」だけを送る

HTTPは最初にページやQRを受け取る用途、WebSocketは接続を保ったままキー状態を往復させる用途です。
`router` は入口の一覧、`handle_client_text` は届いたJSONを種類ごとに振り分ける受付です。

### 関数カード　`handle_client_text`

出典: `C:\00_master\DevApps\APP_KeyDeck01\crates\proto-hub\src\ws.rs` の `handle_client_text`（1144行目付近）

- **役割**: WebSocketの文字列を`ClientMessage`として解釈し、適切な処理へ渡します。
- **呼ばれる場面**: 接続済みブラウザからメッセージが届くたびです。
- **入力**: 接続者ID、Surface種別、JSONテキストです。
- **処理順**: JSON解析 → `key.press`／`deck.press`／`surface.state`／`surface.gesture`の分岐 → 各ハンドラ呼出です。
- **出力**: 直接の値ではなく、状態配信や入力ジョブの登録を行います。
- **失敗時**: JSONが壊れていれば`WS_PARSE`を返し、接続全体をpanicさせません。
- **関連関数**: `handle_key_press`、`handle_deck_press`、`handle_surface_state`、`emit_error`。
- **例え**: 受付が伝票の種類を読み、「鍵の相談」「Deckの相談」「トラックボールの相談」の窓口へ渡す役目です。

### この章でできるようになったこと

- HTTPとWebSocketを使い分ける理由を説明できる。
- ブラウザからのJSONが直ちにWindows入力にならない経路を追える。

### 扱わなかったこと

- 独自の任意メッセージ追加、外部ネットワークでの接続。

### 確認問題

1. `handle_client_text`が直接SendInputを呼ばないのはなぜですか。

## 第7章　Windowsへ入力を渡す

キー名はVK辞書で検証され、文字列の直接入力はクリップボードではなく
`KEYEVENTF_UNICODE`を使います。

### 関数カード　`send_text`

出典: `C:\00_master\DevApps\APP_KeyDeck01\crates\proto-adapter-win\src\lib.rs` の `send_text`

- **役割**: 文字列をUnicode入力としてWindowsへ送ります。
- **呼ばれる場面**: JSONの`text` Actionが許可リストを通って発火したときです。
- **入力**: 入力したい文字列です。
- **処理順**: UTF-16の単位へ変換し、各単位をdown／upの組で送ります。
- **出力**: 成功またはAdapterエラーです。
- **失敗時**: Hub側がエラーとして記録します。どの前面アプリへ届いたかはこの関数だけでは確認できません。
- **関連関数**: `send`、`press_unicode`、`release_unicode`。
- **例え**: クリップボードという共有の机を使わず、文字を1つずつ直接投函するポストです。

### この章でできるようになったこと

### 扱わなかったこと

### 確認問題

## 第8章　押しっぱなしと切断時の解放

ゲームの十字キーは、押下と解放を別々に扱わなければなりません。`send_key()`のように
すぐ離す関数だけでは、押しっぱなしを表現できません。一方で、離す通知が失われると
PC側のキーが押され続けます。そこでKeyDeckは接続者ごとの押下台帳を持ち、切断時に強制解放します。

### 関数カード　`release_held_keys`

出典: `C:\00_master\DevApps\APP_KeyDeck01\crates\proto-hub\src\ws.rs` の `release_held_keys`

- **役割**: 切断したクライアントが押したままのキーをすべて解放します。
- **呼ばれる場面**: ブラウザが閉じる、通信が切れるなど、正常な`Up`を待てないときです。
- **入力**: 接続者IDとHubの状態です。
- **処理順**: その接続者の押下台帳を取り出す → 解放用Actionを作る → adapterの直列ワーカーへ送ります。
- **出力**: 押下台帳からの除去と解放ジョブです。
- **失敗時**: 最善努力で解放し、ログで追跡できるようにします。
- **関連関数**: `handle_key_press`、`fire_action`、adapterの`release`。
- **例え**: 貸出中の鍵を、利用者が帰るときに受付が必ず回収する仕組みです。

### この章でできるようになったこと

- press/releaseと切断時解放が対になって必要な理由を説明できる。

### 扱わなかったこと

- OS全体の非常停止、任意の常駐キーフック。

### 確認問題

1. `KeyHold`の`Up`でも発火が必要なのはなぜですか。

# 第III部　画面を部品から作る

## 第9章　部品を描き、画面を組み替える

`keyboard`、`deck`、`trackball`は画面の部品です。layoutはそれらを`section`へ配置します。
同じ部品を複数のlayoutから参照できます。そのため「全体に効く修正」と「別のものにしたい変更」を
混同しないことが重要です。分けたいときは別IDへ複製します。

### 関数カード　`renderComponent`

出典: `C:\00_master\DevApps\APP_KeyDeck01\static\layout.html` の `renderComponent`

- **役割**: sectionが指す部品種別に応じて、キーボード・Deck・トラックボールを描画します。
- **呼ばれる場面**: Hubから受け取ったlayoutを画面へ表示するときです。
- **入力**: 描画先の要素とcomponent情報です。
- **処理順**: `kind`を見て分岐し、対応する描画関数へ委譲します。
- **出力**: DOMに置かれた部品です。
- **失敗時**: 未知の種別を無理に描かず、設定検証側で防ぐ前提です。
- **関連関数**: `renderKeyboard`、`renderDeck`、`renderTrackball`。現在は共通描画の`static/components.js`も使います。
- **例え**: 組み立て説明書が「この枠には引き出し、この枠には棚」と部品を置き分ける場面です。

### 関数カード　`fitDeck`

出典: `C:\00_master\DevApps\APP_KeyDeck01\static\components.js` の `fitDeck`（共有描画側）

- **役割**: Deckの正方形スロットが区画からはみ出さない大きさを計算します。
- **呼ばれる場面**: Deckを表示し、区画サイズが変わったときです。
- **入力**: 区画サイズ、列数、行数、スロット数です。
- **処理順**: 幅だけでなく高さからも1マスの上限を求め、小さい方を採用します。

- **失敗時**: 最低タップ寸法を守れない構成は、データ設計・検証側で見直します。

### 確認問題

## 第10章　保存できる編集画面にする

現在のトップ画面はレイアウト編集です。保存は、ブラウザから届いた本文をそのままファイルに
書き込む操作ではありません。IDの文字種を確認し、Layoutとして読み直し、`.bak`へ退避し、
全体を再検証します。失敗したら巻き戻します。

### 関数カード　`layout_save_handler`

出典: `C:\00_master\DevApps\APP_KeyDeck01\crates\proto-hub\src\ws.rs` の `layout_save_handler`（390行目付近）

- **役割**: 許可されたlayoutだけを安全に保存し、接続中の画面へ反映します。
- **呼ばれる場面**: 編集画面で保存が要求されたときです。
- **入力**: token、layout ID、layout本文です。
- **処理順**: token確認 → ID検査 → Layoutとして再解釈 → `.bak`退避 → 保存 → `load_startup_data`で全体再検証 → 再配信です。
- **出力**: 保存結果と、成功時の新しい構成です。
- **失敗時**: 不正ID、重なり、参照切れなどをエラーで返し、必要なら`.bak`へ巻き戻します。
- **関連関数**: `layout_id_is_safe`、`startup::load_startup_data`、`broadcast_surface_config_for`。
- **例え**: 書類を提出する前に形式確認をし、控えを取り、全ページが揃うことを確認してから差し替える窓口です。

### この章でできるようになったこと

- 保存APIが「ファイル書込み」以上に検証・復元を必要とする理由を理解できる。

### 扱わなかったこと

- 任意パスへの保存、任意ファイル名の指定。

### 確認問題

1. `.bak`はどの失敗に備えるために必要ですか。
2. 本文をそのまま保存しない利点は何ですか。

# 第IV部　実話から学ぶ

## 第11章　実際に踏んだ落とし穴

ここでは成功談より、設計を変えることになった失敗を扱います。

| 症状 | 原因 | 学び |
|---|---|---|
| 狭いWebViewで13列の右端が消えた | CSS Gridの`1fr`が内容の最小幅を下回れない | `minmax(0, 1fr)`と`min-width: 0`を使う |
| `deck.grid.rows`を変えても段数が変わらない | 型とschemaにはあったが描画・検証で使っていなかった | 宣言の有無でなく、消費箇所まで確認する |
| 押しっぱなしができない | 既存の送信関数がpress直後にreleaseしていた | press/releaseと切断時解放を同時に設計する |
| 区画が重なると片方が消えたように見えた | 画面上の見え方だけでは原因が分からない | layout読込時に重なりを拒否する |
| 編集後に説明文が消えた | 送信しないフィールドが既定値で上書きされた | 往復保存では保持すべき情報をテストする |
| QRで違う画面を開いた | 編集中のlayoutとQRカードを照合できなかった | 編集画面の選択中layoutのQRを直接出す |

### この章でできるようになったこと

- 画面の不具合を「見た目だけ」で直さず、データ・状態・検証のどこで防ぐか考えられる。

### 扱わなかったこと

- 未確認の問題を、既に解決したように書くこと。

### 確認問題

1. `rows`の不具合は、型検査だけではなぜ発見できませんでしたか。
2. 保存で説明文が消えた問題は、どのようなテストで防げますか。

## 第12章　これから安全に変更する

変更は「いまある部品を直す」か「新しいIDへ複製する」かを最初に選びます。既存の利用者に
効いてほしい誤字修正は前者、キー数や配置を変えるような破壊的変更は後者です。迷ったら複製します。

作業の基本順序は、モックまたは設計の裁定 → JSON／実装 → テスト → 実機確認 → Vol凍結です。
