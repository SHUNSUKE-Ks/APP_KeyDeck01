## 2. ここまでに決まった読者体験

読者は非エンジニアを想定します。コードの前の説明が長くなりすぎないよう、処理を小さく分けたコメント付きコード block を中心にします。

各重要な操作は、次の順で説明します。

```text
操作前の実スクリーンショット
  → Hub に渡る情報を記した矢印
コメント付きコード block（赤下線・吹き出しは注釈レイヤー）
  → 確定した結果を記した矢印
操作後の実スクリーンショット

コード block の下: 上から下へ読む主フロー
左右: 必要な説明を最大2本ずつ枝分かれ
各ノード: 詳細説明ページへのリンク
```

図で最も大切なのは、次の3つを混同させないことです。

| 区別 | 読者に見せること |
|---|---|
| Hub の状態変化 | `LayerState` が変わるか。例: `Mo` は変わる。 |
| 画面の変化 | Hub からの配信を受けて、ラベル・盤面などが変わるか。 |
| Windows 入力 | `Fire` により Windows へキーや文字が出るか。`Mo` 単体では出ない。 |

章末確認問題は本文の流れを止めないよう、問題を1ページ、次ページを解答に分けます。

## 3. 最優先で仕上げる第1〜5章

第1〜5章は、各章に以下を揃えます。

- 実在するソースの根拠（絶対パス・関数名）。
- 1関数または小さな分岐に絞った、コメント付きコード block。
- 「役割／いつ呼ばれるか／入力／処理順／出力／失敗時／関連関数／たとえ」を持つ関数カード。
- 実スクリーンショットを使った前→処理→後の状態変化図。
- 中央が縦向きの主フロー、左右が詳細への枝である影響図。
- 図のリンク先となる詳細ページ。
- 章末問題と、次ページの解答。

### 第5章の必須テーマ

`resolve` の説明では、特に `Mo`（momentary layer）を使い、非エンジニアが次を追えるようにします。

1. Fn を Down で押す。
2. `resolve` が `LayerChanged` を返す。
3. Hub のレイヤー状態と画面表示が変わる。
4. **Windows への文字入力は出ない**。
5. Fn を Up で離すと、レイヤー状態が元へ戻る。

`Key`／`TgFire`／`KeyHold` と比較するときも、「状態変化」「Windows入力」「Down/Up」を表で分けます。状態駆動の考え方が、この本で特に丁寧に扱う学習テーマです。

## 5. 根拠にする実装と注意点

掲載コードは必ず実在するものを引用し、説明用に短くした場合は「説明用に簡略化」と明記します。執筆時点で関数名と行の前後を再確認してください。

| 主題 | 主な根拠 |
|---|---|
| レイヤー解決／`resolve` | `crates/proto-keymap/src/lib.rs::resolve` |
| 許可リストの正規化 | `crates/proto-hub/src/state.rs::canonical_command_id` |
| HTTP／WebSocket の入口 | `crates/proto-hub/src/ws.rs::router` |
| WS 接続・キー処理 | `crates/proto-hub/src/ws.rs::handle_socket`、`handle_key_press` |
| Windows 文字入力 | `crates/proto-adapter-win/src/lib.rs::send_text` |
| 画面の Component 描画 | `static/layout.html::renderComponent`、`static/components.js::fitDeck` |

次の線引きは必須です。

- Windows 専用、LAN 内・自分の PC 向けと明記する。
- token 認証、allow list、ロード時検証を外す手順は書かない。
- クライアントは位置 ID または制限済み状態だけを送り、意味の解決は Hub 側で行う。
- `crates/hub-core/` は vendored の凍結コピーであり、KeyDeck 独自実装として説明しない。
- 個人パスは `C:\Users\<user>\Documents\project\...`、IP は `192.168.0.x`、token は `<token>` に置換する。
- 未確認の実機操作、IME 表示の正確性、前面アプリへの text 着地は「未確認」と書く。推測で補わない。
