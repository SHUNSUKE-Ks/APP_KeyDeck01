# n01 — データ形式（keymap / layer / deck / surface / layout）

対象ファイル:
- `schemas/keymap.schema.json`, `schemas/layer.schema.json`, `schemas/deck.schema.json`, `schemas/surface.schema.json`
- `keymaps/keymap_ipad01_vol13.json`（マニフェスト実例）
- `keymaps/layers/ipad01_vol13_layer0.json`（レイヤー実例）
- `decks/deck_default.json` / `decks/deck_story_paths.json`
- `surfaces/trackball.json`
- `layouts/layout_ipad_main.json`

## 役割

これらはすべて「コードを変えずに挙動を変えるための正データ」です。
`schemas/*.schema.json` は「この形でなければ弾く」という契約書、実例JSONは
その契約を満たす具体的な中身です。コードを読む前にこれを読んでおくと、
この後の Rust コードが「このJSONをこう検証しているんだな」と素直に理解できます。

## 読みどころ

### keymap（盤面の入れ物）— `keymap_ipad01_vol13.json`
- 2行目 `"kind": "single"` … 一枚盤面か分割(`split`)かの種別
- 5〜46行目 `"board"` … **盤面の正**。`cols`＝グリッドの列数、`keys[]`の各要素が
  `row/col/colSpan/rowSpan` を持つ。これがそのままCSS Gridの`grid-row`/`grid-column`に
  転記される（設計決定D24）。**位置の情報はここにしかない**。
- 47〜51行目 `"layerFiles"` … このキーマップが読み込むレイヤーファイルの相対パス一覧。
  マニフェスト自身はキーの中身を持たない。中身は別ファイル（下記）。
- keyIdの命名規則（コメント参照）: `K` + 行 + 列2桁。`K103` = row1/col3。
  これを覚えておくとレイヤーファイル側のkeyIdが「盤面のどこか」を頭の中で引ける。

### layer（キー1個1個の中身）— `ipad01_vol13_layer0.json`
- 2行目 `"layer": 0` … レイヤー番号。0番は「基盤」で必ず存在しなければならない
  （後述のD3参照）。
- 4行目以降 `"keys": { "K101": {...}, ... }` … keyIdごとに `label`（表示ラベル。
  改行`\n`で2行表示）と `action`（実際に送る内容）を持つ。
- `action` の形に注目: `{"t":"key","vk":"Q"}` のように `t` がアクション種別、
  残りがパラメータ。26行目の `{"layer":2,"t":"tg"}` はレイヤー2をトグルする、という
  「意味」を持つアクション（=キー入力ではなくレイヤー切替）。
- **ここに書けるvk名は固定辞書のみ**（自由文字列不可）。これが不変条件1の
  「許可リストでしか意味を解決しない」の実体。辞書の正は `proto-keymap`。

### deck（Stream Deck風ボタン集合）
- `decks/` 配下のファイルを開いて構造を見る。`schemas/deck.schema.json` と照合すると
  「grid（何行何列）」「slots（ボタン1個ずつ。id/label/action）」の形が分かる。
  `render:"grid"` は正方形スロット、`"list"` は縦リスト。

### surface（連続値を出す面。トラックボール等）— `surfaces/trackball.json`
- 4〜14行目: `id: "tb01"` の面は `binding: {"t":"mouse.move"}`（動かした量をマウス移動に
  変換する）で、`gestures` にタップ/ダブルタップ/長押しなどの離散操作を定義している。
- 16〜21行目: `id: "tb01-scroll"` は同じトラックボールでも別surfaceとして定義され、
  `binding: {"t":"mouse.scroll"}` を持つ。**1つの物理面が複数のsurfaceIdを持てる**こと
  に注意（クライアントはどのsurfaceIdの動きかを申告するだけで、それが何をするかは
  ここでHub側が決めている＝D28の核心）。
- `clamp` はdx/dyの上限（絶対値）。これを超える値はHub側で拒否される。

### layout（画面の区画割り）— `layout_ipad_main.json`
- 4〜7行目 `"grid": {"cols":12, "rows":9}` … 画面全体のグリッド。
- `sections[]` の各要素が1区画。`row/col/colSpan/rowSpan`（keymapのboardと同じ形）＋
  `component: {kind, ref}` で「どの部品をここに置くか」を指定する。
  `kind` は `keyboard` / `deck` / `trackball` の3種（`crates/proto-hub/src/layout.rs` の
  `ComponentKind` と対応）。
- コメントにある通り、**部品の入れ替えはこのJSONを書き換えて `/api/reload` するだけ**。
  HTMLは触らない。これが「フォーマットの正はデータ、コードは解釈するだけ」という
  このプロジェクトの一貫した方針。

## なぜこうなっているか

- **位置と意味の分離**: `board`/`sections`は「どこに何があるか」だけを持ち、
  「押したら何が起きるか」は`layer`ファイルの`action`が持つ。この分離のおかげで、
  配置だけ変えたい／中身だけ変えたい、という編集がお互いに干渉しない。
- **schemaで形を固定し、コードは中身の整合性（参照先の実在など）を見る**という
  役割分担。壊れたJSONは「起動できない」という分かりやすい形で弾かれる
  （黙って一部だけ壊れた状態で動く、ということがない）。
