# n21 — `static/editor.html`（1512行・フロントエンド最大）

## 役割

トップ画面。レイアウト（区画の並べ方）を編集するPC向け画面
（`/?token=…`、2026-09-07にトップへ昇格。頭コメント参照）。
`static/layout.html`が「実機で使う面」なのに対し、こちらは「その配置を
編集する面」という対の関係にある。

## 前提

- n20（layout.html）とn12（layout.rs）を読んでいること。このファイルの
  データの出どころも同じ`surface.config`（頭コメント12〜16行目）で、
  「エディタが見ている構成と実機の構成が食い違わない」ことが設計上
  保証されている。
- 現時点では**保存ボタンは常に無効**（頭コメント23〜25行目）。
  `layouts/`への書き込みAPI（`/api/layout/save`）は既にws.rs側にあるが
  （n14参照）、このエディタからの保存自体は当時まだ未接続だった、という
  実装状況の食い違いに注意（DEVBOARD等で最新状況を確認するとよい）。

## 読みどころ（規模が大きいので機能ブロックごとに）

- 383〜521行目 `cellSize` / `buildComponentTable` / `buildPalette` /
  `buildSource` / `requiredPx(ref)` / `minCells(ref, grid)` /
  `effectiveMin(sec, grid)` / `fitReport(sec, grid)` … **最小サイズを実データから
  計算する**部分（頭コメント18〜21行目）。キーボードは`board`の列数・行数と
  一番細いキーの`colSpan`から必要pxを算出、Deckはページ送りに回せるので
  下限が小さい、トラックボールは既定値、というルール
  （`brief/ref_component_visual_rules_v1.md`参照）。
- 574〜677行目 `renderPreview` / `iconFor` / `validate(m)` / `render()` …
  区画の見た目プレビューと、レイアウトJSON全体の妥当性チェック
  （n12のRust側検証とは別に、UI上で先に警告を出すためのJS側チェック）。
- 748〜818行目 `returnToPalette` / `notifyReverted` / `isConflicting` /
  `commitOrRevert(sec, before, what)` / `refresh()` … 区画の変更を確定するか
  元に戻すか。「触れる部品パレットへ戻す」という考え方（n01のlayoutコメントに
  あった「パズル」の実装）。
- 1062〜1163行目 `bindDrag(box, sec, handle)`（`begin`/`move`/`end`） … 区画の
  ドラッグ操作。マウス/タッチでの移動・リサイズを1つの状態機械として実装。
- 1201行目〜 `addSection` / `fillLayoutSelect` … 新しい区画の追加、
  レイアウト切替セレクタの構築。
- 1273〜1293行目 `openQr` / `closeQr` … QR表示（他画面と共通のパターン、D25）。
- 1327〜1409行目 `/api/layout/save`への保存リクエスト（2箇所ある点に注目。
  何が違うか実際のコードで確認するとよい）。
- 1430〜1441行目 `connect()` … `surface=layout`で接続。layout.htmlと同じ入口。

## なぜこうなっているか

- 「保存ボタンを黙って無効にしない」（頭コメント25行目）という一文が
  このプロジェクト全体の姿勢を象徴している。機能が未完成でも、
  ユーザーに「なぜ押せないか」を画面上で説明する、という誠実さ。
- 最小サイズを実データ（board/deck/grid）から計算しているのは、
  「見た目のルールを画面ごとに手で調整する」のではなく「データが変われば
  自動でルールも追従する」ようにするため（n15のcomponents.js的な考え方の
  応用）。
