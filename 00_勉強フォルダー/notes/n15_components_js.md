# n15 — `static/components.js`（452行）

## 役割

キーボードとDeckの「JSONをDOMにする」描画処理の**唯一の実装**。1〜13行目の
頭コメントが経緯を語っている: 実機の面（layout.html）と区画エディタ（editor.html）
が別々に描画コードを持つと必ずズレる、という実際に起きた事故（接続先一覧が
main.rsとws.rsに手書きで散っていた話、n05参照）を教訓に切り出された。

## 前提

- n01（keymap/deckの形）、n12（layout.rsのComponent）を読んでいること。
- グローバル関数`KDComponents`として公開され、`<script src="/components.js">`を
  読み込んだページから呼ばれる（読み込む側はn20 layout.html、n21 editor.html）。

## 読みどころ

- 15〜25行目 **2つのモードの説明**が最重要:
  - `interactive: true/false` … 押下でHubへ**送るか送らないか**
  - `editable: true/false` … 触れる（クリック/ドラッグできる）か**できないか**
  - 「送らない」と「触れない」は別の軸。まとめて扱うと編集画面の盤面まで
    `pointer-events:none`になり指でもマウスでも反応しなくなった、という
    実際の不具合が20〜22行目に書かれている。**この2軸の分離を理解するのが
    このファイルを読む最大の目的**。
  - 「送信そのものはここに書かない。何を送るかはホストが決める」（24行目）
    ＝ 不変条件1がフロントエンドの設計にも及んでいる証拠。
- 133〜182行目 `injectStyles` / `resolveDisplay` / `renderLabel` / `oops` …
  CSSの1度きりの挿入、レイヤー状態からラベルを解決する処理、エラー表示。
- 183〜257行目 `renderKeyboard(host, keymap, state, options)` … n01の`board`を
  読んでDOM要素を組み立てる中心関数。`bindKey`（234行目）でpointerdown/upを
  登録する（`interactive`のときだけHubへ送るコールバックを呼ぶ）。
- 258〜322行目 `renderDeck(host, deck, options)` / `fitDeck`（323行目） … Deckの
  格子（grid/list）を組み立て、コンテナに収まるようスロットサイズを計算する。
- 369〜413行目 `renderNav` / `showTokenNotice` … 画面間ナビゲーション（他の面へ
  移動するセレクタ）とトークン関連の注意表示。ページ本体というより共通UIパーツ。

## なぜこうなっているか

- 「描画はここにしか書かない」という規約により、盤面の見た目を変えたいときは
  1ファイルを直すだけで実機面・編集画面の両方に反映される。逆に言うと、
  もし将来ここを経由せず個別のHTMLに描画ロジックを書き足すと、この規約が
  破られてまた同じ種類のズレ事故が起きる。
- CSSも同じファイルに持たせている（27〜29行目）のは、見た目が2箇所に分散する
  ことを避けるため。`var(--panel, 既定値)`の形にして、ホスト側がCSS変数を
  定義していればそちらが勝つようにしている（ホスト固有の配色を壊さない）。
