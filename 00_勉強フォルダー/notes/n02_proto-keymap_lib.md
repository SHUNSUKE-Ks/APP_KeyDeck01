# n02 — `crates/proto-keymap/src/lib.rs`（1646行）

## 役割

キーマップの型定義・JSONロード＆検証・**レイヤー解決エンジン**を持つ、
このプロジェクトの一番下の層。標準ライブラリのみに依存する（1〜5行目のコメント参照）
＝ サーバやWindows APIのことを一切知らない、純粋なドメインロジック。

## 前提

- n01（データ形式）を先に読んでいること。ここで出てくる`Keymap`/`Layer`/`Board`は
  n01で見たJSONがそのままRustの型になったもの。
- 「マニフェスト」＝`keymap_*.json`、「レイヤーファイル」＝`layers/*_layerN.json`
  という呼び分けを覚えておく。

## 読みどころ

- 76〜135行目 `KeymapError` / `is_known_vk` … vk名の固定辞書と、辞書外を弾く関数。
  ここが「クライアントは自由な文字列を送れない」の土台。
- 137〜273行目 `Action` enum … `Key{vk}` `Chord{keys}` `Mo{layer}` `Tg{layer}` `Trans`
  `None` `KeymapSwitch{id}` `KeymapReset` `Text{string}` など。**盤面が意味づけできる
  「できること」の全種類がここに列挙されている**。何か新しい機能を足すときは、
  まずここに新しいバリアントを足すところから始まる。
- 220〜273行目 `KeyDef` / `Layer` / `Half` / `Halves` / `Board` / `BoardKey` … n01で見た
  JSON構造に対応する型。`Board`がグリッド式（D24）。
- 349〜538行目 `load_keymap_from_path` / `load_keymap_with` … マニフェストを読み、
  `layerFiles`を相対パスで解決して全部読み込み、結合してから検証する処理。
  「ファイルごとに検証」ではなく「全部読み終えてから1回で検証」という順序に注意
  （コメント18〜19行目）。
- 539行目〜 `validate_merged` … 検証本体。「Layer0必須」「Layer0にtransは禁止」
  「vk辞書外」「mo/tgの参照先レイヤーが実在するか」などをチェックする。
- **684〜842行目が本体**。ここだけは行き来しながらじっくり読む価値がある:
  - `Edge`（Down/Up）、`LayerState`（`momentary`・`toggled`の2集合）
  - `LayerState::active_layers()`（716〜722行目）: **有効レイヤー = {0} ∪ momentary ∪ toggled**
    （`CLAUDE.md`の不変条件2＝設計決定D3そのもの）
  - `resolve()`（746行目〜）: 1つのkeyIdの押下/離しを受け取り、
    1. そのkeyIdがどの層にも存在しなければ`UnknownKey`
    2. 有効レイヤーを**番号の大きい順**に見て、`Trans`でない定義に最初に当たった
       ものを採用する（フォールスルー。761行目 `!matches!(def.action, Action::Trans)`）
    3. 見つからなければ`NoResolution`
    4. 見つかったアクションの種類ごとに分岐して`Resolved`を返す
       （`Mo`/`Tg`はレイヤー状態を変えるだけ、`Key`等は`Fire`、`KeyHold`は
       upでも発火する唯一の例外、など）
  - この関数は**乱数も時刻も使わない**（744行目のコメント）＝同じ入力列は必ず同じ
    結果列になる（決定性・G5）。テストが書きやすく、バグ調査もしやすい理由。

## なぜこうなっているか

- レイヤー解決を「Hubのどこか」ではなくこの独立crateに閉じ込めているのは、
  WebSocketの都合やWindows APIの都合から完全に切り離して、
  「入力→状態→出力」というルールだけをテストできるようにするため
  （`mod tests`が849行目から続く）。
- `Action`にHub側でしか扱わない種類（`MouseMove`等）も混ざっているのは、
  「送信できる意味の全種類」を1箇所に集約するため（正は1箇所、の原則）。
