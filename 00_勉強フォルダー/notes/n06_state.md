# n06 — `crates/proto-hub/src/state.rs`（404行）

## 役割

Hubの状態を一元的に持つ`HubState`（と、それを複数スレッド/接続から安全に共有する
`SharedState = Arc<Mutex<HubState>>`）を定義するモジュール。ws.rsの全ハンドラは
最終的にここへ触りに来る。「今どのキーマップがアクティブか」「どのクライアントが
繋がっているか」「トークンは何か」などの**唯一の正**。

## 前提

- `SharedState`は`Arc<Mutex<HubState>>`（14行目）。複数のWebSocket接続が同時に
  同じ状態を読み書きするので、必ずロックを取ってから触る、という前提でコードが
  書かれている。

## 読みどころ

- 16行目 `PORT: u16 = 8770` … サーバのポート番号。
- 21行目 `IPAD_KEYMAP_ID` / 25行目 `DEFAULT_DECK_ID` … 「省略時のデフォルト」を
  表す定数。iPad面は常にこのキーマップに固定され、分割面のキーマップ切替の
  影響を受けない（18〜20行目のコメント）。
- 31行目〜 `SurfaceKind`（Split / Ipad / Trackball ...）… WS接続が「どの面か」を
  表す区分。面によって共有する状態が違う（27〜29行目のコメント）。
- 59〜93行目 `AccessToken` … トークンの生成・検証。`is_valid`（81行目）が
  **定数時間比較**（`subtle::ConstantTimeEq`、3行目でimport）を使っている点に注目。
  文字列の`==`ではなくこちらを使うのは、タイミング攻撃（比較にかかった時間から
  正解を推測される攻撃）を避けるため。
- 94〜112行目 `canonical_command_id(action)` … あるActionを「コマンドID」という
  正規の文字列に変換する関数。hub-coreの`CommandService`（冪等判定）に渡すための橋渡し。
- 113〜308行目 `HubState`本体。フィールドと主要メソッド:
  - `new(...)`（160行目）… 起動時に一度だけ呼ばれるコンストラクタ。main.rsから
    渡された`keymaps`/`decks`/`surfaces`/`layouts`等をまとめて受け取る。
  - `layer_state_for(keymap_id)`（209行目）… キーマップIDごとに独立した
    `LayerState`を返す。**盤面ごとにレイヤー状態が別々に管理される**ことがここで分かる
    （n12のlayoutで複数キーボードを1画面に置けるのはこの独立性のおかげ）。
  - `find_deck_slot`（215行目）… deckId+slotIdからスロットを引く。
  - `connection_url`（221行目）… ある接続先(target)へのURLを組み立てる。
    main.rsの起動バナー・ws.rsのformats API・settings画面が全部これを使う。
  - `register_client` / `unregister_client` / `send_to` / `broadcast_to`
    （257〜314行目）… WebSocket接続の登録・解除・個別送信・一斉送信。
  - `note_key_hold` / `take_held_keys`（267〜286行目）… **押しっぱなしキーの追跡**。
    クライアントが切断されたときに「押されたままのキー」を離す処理
    （ws.rsの`release_held_keys`から呼ばれる）と対応している。
- 309〜334行目 `AdapterJob` / `spawn_adapter_worker()` … Windowsへの送信を
  専用の非同期タスクへキューイングする仕組み。WSのハンドラが直接SendInputを
  呼ぶのではなく、チャンネル経由でジョブを渡している（直列化のため）。

## なぜこうなっているか

- 状態を1つの構造体・1つのMutexに集約しているのは、「分割キーボード2台が
  同じレイヤー状態を同期して見る」「どのクライアントも同じ構成を見る」ことを
  保証するため。分散させると同期漏れのバグが起きやすい。
- トークン比較に定数時間比較を使うのは、D8（トークンは起動のたびに変わる）を
  実際に安全にするための細部。ここを疎かにすると「毎回変わるトークン」の
  意味が薄れる。
